# Plan 024 Task 5 (R15, patch-safe part): faster SHA-256 and one-pass canonical JSON

Question: does a tighter pure-JS `sha256`, an ASCII fast path in `utf8()` and a single-traversal `canonicalJson` give the plan's 2× per MB on `sha256`, with hashes and errors byte-identical to 0.2.2?

Answer: hashes and errors are identical, and every stage is faster, but `sha256` itself reaches about 1.3–1.5×, not 2×. `utf8()` on ASCII is about 3× faster and `canonicalJson` about 1.5×. Overall, `packageHash` takes 0.70–0.77 of its 0.2.2 time.

Regenerate the A/B figures with:

```bash
timeout 900 bun bench/ab.ts <base-ref> bench/hash.bench.ts --runs 9
timeout 1500 bun bench/ab.ts <base-ref> bench/render.bench.ts --runs 7 --metric agent-home-renderKey.ms
```

`<base-ref>` is the commit before plan 024 Task 5 (`5473c39`).

## What changed (`src/pack/hash.ts`)

- `sha256`: full 64-byte blocks are read straight from the input as big-endian words. 0.2.2 copied the whole input into a padded buffer and read it through a `DataView`. Only the unaligned tail goes into a 64- or 128-byte block. The schedule `w` and the state are module-level `Int32Array`s, allocated once. The working variables are locals, and `| 0` keeps every sum a 32-bit integer. The rotations are written out inline. `Ch` and `Maj` use their one-operation-shorter forms. `>>> 0` appears only when the digest is printed.
- `utf8()`: an ASCII prefix loop writes into an exact-size buffer and returns it when the text is all ASCII. On the first non-ASCII unit it grows to the worst case for the rest. Lone surrogates are found inside the encoding loop (same `TypeError` and message), so the separate regex scan over the whole text is gone.
- `canonicalJson()`: one iterative walk both checks that the value is JSON (non-finite numbers, non-JSON types, cycles through an ancestor set, non-plain prototypes) and writes the text. Scalars are serialised as their parent is expanded, so only containers go on the stack. A lone surrogate is recorded and thrown after the walk, so a value that is both non-JSON and has a lone surrogate still reports "Expected a JSON value", as 0.2.2 did when `validateJson` ran first. `validateJson` is no longer imported by `/pack/hash.ts`.

## Proof of identical output

- The existing `sha256_nist_vectors`, `sha256_matches_bun`, `canonical_json_*`, `meta_changes_hash` and `render_key_*` tests and all of `hash-vectors.test.ts` (the `conformance/hash/` vectors) pass unedited.
- New tests in `src/__tests__/pack-hash.test.ts`:
  - `sha256_matches_native_on_random_inputs`: every length 0–200 (all padding boundaries), 10,000 random byte arrays of 0–4,096 bytes, and 1 MiB and 16 MiB inputs, against `Bun.CryptoHasher`. That is the native oracle the file already used; the plan named `node:crypto`, which is equivalent, and `Bun.CryptoHasher` keeps the test Bun-only. It stays test-only.
  - `utf8_matches_text_encoder_and_rejects_lone_surrogates`.
  - `canonical_json_errors_unchanged_for_non_json`: `NaN`, `undefined`, `1n`, a symbol, a cycle, a nested `Date`, lone surrogates in strings and keys, mixed cases, and a shared (non-cyclic) reference.
- A throwaway differential (not committed) ran the 0.2.2 `hash.ts` (`git show 5473c39:src/pack/hash.ts`) beside the new one: 60,000 random values (half with non-JSON values, lone surrogates, cycles and foreign prototypes mixed in; 22,916 of them throw), plus a DAG, a null-prototype object, an own `__proto__` key, a class instance and a 100,000-deep array, compared on output text or on error class and message. It also compared 30,000 random `utf8()` strings over the encoding edges. No differences.

## A/B results

Host load 25–39 (a QEMU VM holds the CPU), so single ratios carry about ±10 points of noise. `bench/hash.bench.ts` (new; 1 MiB inputs, medians of 15 calls per run):

| Metric | Run 1 ratio (load 34–39) | Run 2 ratio (load 25–29) |
| --- | --- | --- |
| `sha256.msPerMiB` | 0.654 (36.4 → 23.4 ms) | 0.825 (34.2 → 28.2 ms) |
| `utf8.asciiMsPerMiB` | 0.334 | 0.365 |
| `utf8.mixedMsPerMiBChars` | 0.790 | 0.690 |
| `canonicalJson.ms` (256 KiB code and 2,000 rows) | 0.678 | 0.650 |
| `packageHash.512KiB.ms` (512 KiB code and 2,000 rows) | 0.774 | 0.698 |

Run 1 was taken before `utf8()`'s multi-byte loop was split into `encodeRest` for the complexity lint. Run 2 is the committed code.

In-process interleaved runs (25 alternating rounds on 1 MiB, the same machine, load about 32) give a cleaner `sha256` reading: new/old 0.695, 0.715 and 0.749 over three runs, which is 1.3–1.4×.

`renderKey` on the render bench's agent-home inputs (`agent-home-renderKey.ms`, 7 paired runs, load 16–30): 3.78 → 3.29 ms, ratio 0.836. No regression. The render bench's own wall-clock budgets fail under this load on both sides; the `renderKey` figure is informational and was recorded under `--json`.

## Variants tried and dropped

All three were throwaway scripts in the session scratchpad, measured in-process against the current code and 0.2.2:

| Variant | Against the committed code | Against 0.2.2 |
| --- | --- | --- |
| Rounds unrolled by 8 (register renaming, no shuffle) | 0.89–0.94 | 0.65 |
| Fully unrolled 64 rounds with literal constants | 0.83 | 0.59 |
| Schedule and state passed as parameters, not module scope | noise (0.87–1.16) | — |

Even the fully unrolled form reaches only 1.7× against 0.2.2 on this host and JIT (Bun 1.4.4, JavaScriptCore), and it costs a generated 64-round body. Neither unrolled form brings the plan's 2× within reach, so the compact loop is kept.

## Against the plan's targets

- `sha256` 2× per MB: **missed**. About 1.3–1.5× (A/B 0.654 and 0.825; in-process 0.70–0.75). The ceiling that was measured (full unrolling) is about 1.7× on JSC.
- `packageHash` on 512 KB from about 9.9 ms to 5 ms or less: not reproducible as an absolute figure on this host (0.2.2 reads 68–80 ms here for a 512 KiB package with 2,000 manifest rows). As a ratio, 0.70–0.77.
- `renderKey` does not regress: met (0.836).
- Hashes and errors byte-identical: met.
