# Decision: Release 0.3.0 scope

## Decision

0.3.0 includes everything already queued and every weakness and lesser gap identified in the 2026-11-05 evaluation. It is a large minor release that may break contracts with migration entries. No Node runtime support is maintained: backend subpaths stay Bun ≥ 1.4.2, and the archive gate Node probe remains a portability probe only. The isolated runner ships as the separate optional package `@arnilo/liveframe-runner-quickjs`; the starter is `@arnilo/liveframe-starter`.

Freeze the public surface at v0.2.3. Use one comparator and a 0.3.0 register; removed and changed entries must name an actual heading in `docs/migration-0.3.md`. Every break also receives a spec update and CHANGELOG line in its implementation task. No version bump or publication is authorized by this decision.

## Context

0.2.2 required additive, opt-in changes and deferred breaks. 0.2.3 kept an empty register. The minor release is the agreed window for those deferred changes and the broader runtime-UI evaluation findings. Plans 026–032 divide that scope into independently checked tasks.

## Not in scope

- Nested surfaces: composition through dependencies and coordination covers the identified need; lifting spec §6.4 changes every sheet and remains deferred.
- A second renderer: the framework-independent surface core provides its prerequisite without adding another implementation.
- Node runtime support: excluded by the owner; the Node archive probe does not establish support.

## Plan 025 carryovers

- Task 8 remains open: quiet-host benchmark proof moves to plan 032 Task 3. No new performance claim is made here.
- Task 10 remains open: owner repair of the npm next dist-tag moves to plan 032 Task 5. The published 0.2.3 latest release and completed Task 11/11a are not reopened.

## Alternatives Considered

1. Keep 0.3.0 small or postpone evaluation findings: rejected by the explicit big-release scope.
2. Allow unregistered breaks: rejected because hosts need visible contract changes and actionable migration instructions.
3. Keep comparing the checkout against 0.2.1 and 0.2.2: rejected because intended minor-release breaks would fail redundant patch-release gates; 0.2.3 is the latest baseline.
4. Keep Node runtime support or bundle the isolated runner into the core: rejected by the owner runtime and optional-package decisions; core remains host-API-free.

## Rationale and Evidence

The plan scope table combines the prior node-reference, extension-property and variant-axis decisions, compatibility deferrals, backlog and evaluation items. The accepted 0.2.2 and 0.2.3 decisions explain why breaks waited for this minor. The published v0.2.3 tag is the reproducible baseline, generated with a frozen install and build in a detached temporary worktree. Plan 025 and roadmap §3 still record the two open release proofs above.

## Consequences

- Plans 026–031 implement the approved scope; plan 032 performs release proof and publication separately.
- Hosts and independent ports must follow each implemented break in the migration guide.
- The register starts empty; future tasks must classify their changes and keep the gate green. Declaration equality cannot detect behavior-only breaks, which still require explicit migration and regression evidence.
- Revisit the scope only with owner approval if implementation evidence invalidates a design or release gate.
