# Decision: Release 0.2.3 scope

## Decision

Release 0.2.3 ships every fix from the 2026-11-03 comprehensive code review of `main` at `9894b1d` (findings R1–R26), **unless the fix changes the public API**. An API-changing fix moves to 0.3.0 with a migration entry. 0.2.3 adds **no declarations**: the API register `scripts/release/api/register-0.2.3.json` stays `[]`, and the checkout is compared against the frozen `0.2.2.json` baseline. The five split findings (R4, R8, R9, R15, R24) are split as in the table below. The sucrase change (R11) is approved: bundle sucrase's `transform` into `dist/pack` and move `sucrase` to `devDependencies`, gated on byte-identical hash vectors.

## Context

Plans [023](../plans/023-Phase-7-Part-J-Release-0-2-3-Security-And-Defects.md), [024](../plans/024-Phase-7-Part-K-Release-0-2-3-Performance.md) and [025](../plans/025-Phase-7-Part-L-Release-0-2-3-Simplification-And-Release.md) implement the review fixes. 0.2.2 is published (plan 022 complete). The 0.2.2 rules allowed additive register entries; the owner's rule for 0.2.3 is stricter, and an empty register is its only mechanical reading.

The review found these classes of problem:
- contract gaps (custom runner trees not host-validated, a `await using` bypass of the synchronous-module rule);
- cache weaknesses (failed links cached, identity-keyed hash cache);
- small defects (worker error results, `listPlacements`, MCP path leaks, `fr` on dimension props);
- supply-chain gaps (no audit or SBOM, a publish that can run from a branch, sucrase's CLI-only dependencies);
- performance hot spots;
- duplication, dead code and long closures.

The owner then answered "Approve all" to the confirmation of the five split rows (R4, R8, R9, R15, R24) and the sucrase dependency change (R11), as written in plan 023.

## Rules this decision adds

- **The 0.2.3 register is empty.** A task that needs a register entry has found an API change. It stops, and the item moves to `docs/compatibility.md` § "Deferred to 0.3.0", with the owner's acknowledgement recorded in the task notes.
- **Outcome changes only for invalid input.** A fix may change an outcome only for input the spec already calls invalid (an invalid tree, a forbidden module construct, a corrupted record). It gets a CHANGELOG "Fixed" line.
- **Sucrase bundling (R11) is conditional on evidence.** It lands only when the bundled `pack()` output is byte-identical on every hash vector and corpus package hash, `pack()` time stays within 5%, and sucrase's MIT licence text ships in `dist/`. Otherwise Task 9 records the failure and a P3 backlog entry.

## Alternatives Considered

1. **Replace the 0.2.1 baseline with 0.2.2.** Rejected: it edits an existing assertion, and keeping both costs nothing.
2. **Allow additive register entries, as 0.2.2 did.** Rejected: the owner's rule is "unless there are API changes".
3. **Ship every fix in 0.3.0.** Rejected: most fixes change nothing observable except for invalid input, and the owner wants them out now.
4. **Keep sucrase as a dependency.** Rejected: seven unpinned transitive packages (`commander`, `mz`, `thenify`, `pirates`, `tinyglobby` and others) ship to every consumer for one function.
5. **Use Bun's transpiler instead of sucrase.** Rejected: it is not host-API-free, and `/pack` must run under Node.
6. **Use npm `overrides` to pin sucrase's dependencies.** Rejected: overrides do not apply to consumers.

## Rationale and Evidence

- The empty register makes the owner's rule mechanical: `compareApiSurface(baseline022, current, [])` fails on any changed declaration, schema, corpus case or vector.
- The split rows each have a patch-safe part (a snapshot, relative paths, documentation, a speed-up, a differential test) and a part that changes an observable contract (freezing packages, a handle-based read, rejecting `fr`, a verified-package cache option, a single-source format definition), which goes to 0.3.0 or the backlog.
- R11: sucrase's runtime code is a single function, and its other dependencies serve only its CLI. Bundling it removes them from every consumer's install, and the lockfile pins what is bundled.

## Consequences

- Plans 023–025 cannot change a declaration, a schema, a corpus case or a vector. `src/__tests__/api-stability.test.ts` enforces this at the end of every task.
- The 0.3.0 migration list gains: package freezing (R4/R5), rejecting `fr` on dimension props (R9), a verified-package cache option (R15). The backlog gains a handle-based draft read (R8) and a single source for format definitions (R24).
- A consumer that imported `sucrase` transitively must depend on it directly (CHANGELOG "Changed").
- Revisit if a task finds that a fix cannot avoid a declaration change, or if bundling sucrase cannot reproduce every hash vector.
