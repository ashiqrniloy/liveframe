## Task 3 — theme authority and vocabulary

- **Rack typography ownership:** Clay's `packages/design-rack/docs/index.md` §2 and decision `2026-08-28-2234` separate content themes, user typography and design systems. The Rack primary hover recipe retains its source opacity of 0.86; the additional `accent.fill.hover` alias does not invent a new palette entry.
- **Roles absent from Certified:** `surface.case/module` alias bg/surface; text meta/disabled and kbd/status reuse its muted/foreground roles; border roles reuse line/line-2/control/focus. It also has no diagnostic fill roles: diagnostic soft roles reuse its neutral hover wash, preserving its no-chromatic-fill direction. These aliases satisfy the structural switch contract but do not prove Rack's identity-versus-status distinction under Certified; Task 10 must inspect this, and Task 12 must report the limitation.
- **Transparency:** Rack's 247 translated source recipes replace `transparent` with the recipe keyword `none`; no zero-alpha theme role is needed. Every other source recipe field and all 14 source values are retained. Tests compare with the pinned manifest after that sole normalization, including nested shadow roles.
- **Scope:** only Certified light and Modus Operandi light are supplied. Dark/contrast modes, OS forced colours, font loading and pixel parity are not established by this data task; CSS projection and parity belong to Tasks 5 and 11. Typography sizes and spacing are numeric CSS pixels; rem-based Certified tokens use the reference's default 16px root.

## Plan 002 Task 3 — design values and the new style props

- **Declared values have no source counterpart in either artifact.** Certified's rail is the raw rule `grid-template-columns: minmax(0, 1fr) 22rem` and its single-column switch is the viewport media query `(max-width: 900px)`, not a design value. Rack declares no `size.rail` or `bp.md`. Task 3 publishes them as app-declared design values (`size.rail: 352`, `bp.md: 720`) because spec §6.2–§6.3 require named, container-keyed values rather than raw lengths or viewport queries. A 720 px container breakpoint keeps the three compared widths on the same side as the artifact's 900 px viewport rule; a narrower slot or a viewport-different container can still split differently, which stays a parity finding.
- **The query container is emitted only when a surface uses a responsive value.** `container-type: inline-size` applies layout containment to the whole subtree, and the Plan 001 switch budget measured 34–44 ms per stylesheet activation on the agent-home queue when the root was always a container, against the 16.67 ms budget. A surface whose tree has no responsive style therefore gets the surface typography class but no container; a surface that uses one gets both. The projection and container rules are identical either way. This is a measured deviation from "each surface root gets `container-type: inline-size`" and is recorded here for the Task 5 budget decision.
- **Rack typography additions have no Rack source.** Rack's source recipes set no `font-family` on button, tab, field-label, trigger, dialog-title or tooltip slots; it relied on the embedding page's fonts. Task 3 assigns each text slot a Rack typography role so no surface text falls back to host fonts (spec §6.2 G12). This is a deliberate completion of Rack's incomplete vocabulary, not a translation of a source recipe.
- **Certified's fill roles stay meaning-only.** `fill` accepts status, diagnostic, patch and accent roles. Certified aliases several diagnostic and patch roles to its accent/foil palette, so two different fill meanings can paint the same colour; Rack keeps its own status colours. Fill therefore carries meaning, not a distinct paint per role, and Task 5 must not treat matching colours as matching semantics.
- **Rack has no `size.rail` or `bp.md`.** Both design systems define every declared value name to keep the declaration closed. Rack's values are proof-grade choices with no Rack source, and the Rack module keeps its fixed two-column composition; responsive Rack layout remains a Task 5 measurement.

## Plan 002 Task 4 — disclosure, semantics, button state and box variants

- **Rack maps the new slots to its nearest families.** `disclosure.default.root` ← `collapse.default.root`, `summary` ← `collapse.default.header` (hover/focus included), `panel` ← `collapse.default.body`. `box.plate.root` ← `panel.default.root`, `box.rule.root` ← `divider.default.root`, `box.callout.root` ← `panel.tint.root`, and every box `rail` ← `divider.default.root`. Rack has no `.disclose`, `.plate` or `.callout` geometry: the collapse header is its own rounded surface rather than a summary row, and the callout rail is a full divider rather than the artifact's 1 px hue rule. The `rail` slot exists on every box variant because recipes are keyed per slot; the renderer draws it only for `callout`.
- **Native `details`/`summary`, not React Aria's `Disclosure`.** React Aria Components 1.22.1 renders a `div` + heading + trigger button with `aria-expanded`, while the artifact (`details.disclose`) and the required keyboard behaviour (Enter and Space on a focusable summary) are native. The native element keeps the artifact's DOM, gives both keys without extra wiring, and a local toggle sends no intent; a Chromium test covers the toggle, focus retention across a revision, and a host-supplied `open` change.
- **Box variants inherit the layout model, not the reference geometry.** The recipe language has one border colour/width for all sides, so `box.rule` draws a hairline box where `.line` draws top and bottom rules only. `box.plate` uses the mount shadow and plate radius but cannot reproduce the artifact's well tray and 5–6 px ring (`--mk-cut`, ring on neighbours). `box.callout` fixes the rail to `border.subtle`; the artifact tints the rail per `data-tone` (attention, danger, success, accent, info) and the box has no tone prop, so per-tone rails remain a Task 5/11 composition decision rather than a recipe tweak.
- **`terms` is a content rule, not a child-kind rule.** `term` and `detail` are `semantics` values on layout primitives (per spec §5), so the validator checks `terms` children and the parent of `term`/`detail` by their `semantics` prop rather than by kind. This keeps the catalog at 24 kinds and still rejects a term outside terms, a foreign child inside terms, an unknown semantics value and a label over 80 characters.
- **Button `pressed` is presentational.** It renders `aria-pressed` but sends no toggle intent: there is no `onChange` on `button` and the plan gives it no state contract. A consumer that needs toggle state uses `onPress` and host state. `current` renders `aria-current="true"` only when true.
- **Disclosure open styling is partly base CSS.** Native `summary` exposes no `aria-expanded`, so the `open` state recipe on the root matches `[open]`, while the summary's open-only margin lives in the projection's base layout rule (layout, not a recipe, so it adds no colour or geometry data).

## Plan 002 Task 5 — recomposed queue and the container-query switch cost

- **The queue's two-column layout uses flex wrap, not the responsive grid.** A measured finding: any surface whose tree carries a responsive style gets `container-type: inline-size`, and on this page a design-system switch then costs 26–44 ms (switch sample max; budget 16.67 ms) versus 3.4 ms without it. The containment, not the `@container` rule count, is the cause: removing every responsive rule while keeping the container stays at 42 ms, and scoping the container to the nearest parent of the responsive node does not help. Chromium must lay out the contained subtree to resolve container conditions after the theme sheet flips, and the queue's ~110 elements with two custom faces exceed the frame budget. The composition therefore uses `Inline wrap` with the focus at `width="size.rail" grow={1}` and the rows at `width="size.rail" shrink={1}`: two tracks from ~728 px up, one track below. The declared breakpoint is 720 px, so widths between 728 and 720 differ from the artifact's rule; none of the parity widths (1440, 1024, 390) falls in that band. The responsive API and its container-query test stay; this is a composition choice, recorded for the owner, not a capability removal.
- **The flex threshold is 8 px above the declared breakpoint.** It is the sum of the two `size.rail` bases plus one `space.5` gap. If Task 6 needs an exact 720 px transition, the container-query cost above has to be resolved first (a host-width attribute or a different measurement) rather than raising the switch budget.
- **Live run of the recomposed queue** at 1440/1024/390: focus 1016/600 px beside a 352 px rows rail, and at 390 both 342 px stacked; the rows rail shrinks with the container instead of overflowing.
- **Render bench: the recomposed queue exceeds 2 ms.** `agent-home` now renders 462 nodes at 50 rows (193 before: each row gained a marker icon, a flex line and the folded-alert flag), and the bench measures 5.9–6.5 ms mean under this machine's load (load average ≈ 12; the pre-Task-5 tree measured 2.1 ms on the same run, so the budget is also load-sensitive here). Reaching 2 ms needs either fewer than ~250 nodes — impossible while keeping the artifact's marker, `aria-current` button and folded-alert flag in each row with the current style-prop surface on `box` but not `inline` — or a cheaper per-node render. Recorded per the plan's rule; the budget is not raised.
