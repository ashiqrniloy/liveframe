# What 0.2.0 gives adopters

Every request in [Synapta's list](https://github.com/ashiqrniloy/liveframe/blob/main/plans/requests/synapta-adoption-requests.md) (LF-01 to LF-17) and [Clay's list](https://github.com/ashiqrniloy/liveframe/blob/main/plans/requests/clay-adoption-requests.md) (CL-01 to CL-09), plus the backlog items they raised, and what shipped for it. Each row states the general problem first: the two apps are the evidence, not the reason. Section numbers are the [spec](spec.md); the [changelog](../CHANGELOG.md) lists the changes, and [the migration guide](migration-0.2.md) covers the three breaking ones.

Where a row says a limitation, it is part of the release, not a to-do. The row is what an adopter can rely on today.

## Synapta requests

| ID | Problem, in general | Shipped in 0.2.0 | Spec | Limitation |
| --- | --- | --- | --- | --- |
| LF-01 | The host is told an intent happened but not where it came from, so it cannot check that the served tree offered it. | `onIntent(intent, origin)` with `IntentOrigin = { surfaceId, revision, nodeId, event }`, and `checkOffered(tree, origin, intent, validator)` at the root export; also on `<Preview>` and preview sessions. | §8, §11 | `checkOffered` is a helper the host calls; nothing enforces it. The host still re-checks arguments on dispatch. |
| LF-02 | Codegen and capture exist but are reachable only through the CLI and MCP, not from a build service. | `generate()`, `generateDefinitions()` and `generateElementsSchema()` from `/sdk/gen`; `capture()` from `/preview/capture`. | §7.2, §7.5, §13 | Capture requires an injected `CaptureBackend`; importing the subpath loads no browser driver. |
| LF-03 | Shipped docs described shipped APIs as future work. | Wording corrected across the guides, with a CI test (`docs-wording`) that fails when a sentence calls an exported name planned. | §7.2 | The test matches sentences, not meaning; a genuinely future feature may still be described in prose as future. |
| LF-04 | The schema language cannot say "non-empty", "list of mixed record kinds" or "value or null", so constraints move into widget code where agents cannot read them. | `minLength`, `minItems`, `nullable` on any form, and discriminated unions `{ discriminator, mapping }`; `Infer` and `liveframe gen` follow. | §5 | No general `oneOf`/`anyOf`, by design. `pattern` stays banned in widget-authored schemas. |
| LF-05 | A form with N fields cannot submit once without N round trips, or a stale submit if the last commit has not re-rendered. | Object-carrying events: `carries: { object: <closed schema> }` with `bindAll` on the action, plus `setState` into an object-typed key. | §8, §9 | The object must be a closed, bounded schema; the validator checks it against the action's arguments at render time. |
| LF-06 | State is keyed by placement only, so a shared placement cannot hold per-viewer state without duplicating placements. | `putState`/`getState` take `(placementId, scope)`; `loadPlacement` takes `{ scope, state }`; `verifyPlacementInputs` for hosts with no store; `fileStore` reads a 0.1.0 directory. | §7.4 | Scope is an opaque host string of at most 128 code points. Named scopes are not readable by 0.1.0, so a rollback loses them. |
| LF-07 | A widget cannot describe itself, and a host cannot bind its own facts to the immutable package. | Manifest `description` and closed `meta`; capability `meta` per action and source; `description` shown by `list_capabilities`. | §7.3 | `meta` is hashed and carried but never interpreted, and grants nothing; MCP hides it unless the authoring config opts in. |
| LF-08 | The browser primitive that raises an action cannot tell whether it is confirmed or irreversible, so the label and the confirmation step are left to each widget. | Capability `irreversible`; an `events` map in the `implement()` context exposing `{ type, confirm, irreversible }`; `<Surface confirm={(intent, meta) => Promise<boolean>}>` awaits approval before `onIntent`. | §5, §8, §11 | Confirmation is presentation, never authorisation; the host still authorises on dispatch. |
| LF-09 | Structure a page needs — a form landmark, a labelled group, a figure, a live region — cannot be expressed, so status and errors go unannounced. | `semantics` gains `form`, `group`, `figure`, `status` and `alert`. | §5, §11 | Tables stay a host primitive with its own `a11y.role`; the list is library-fixed, so a catalog cannot add values. |
| LF-10 | An installed theme can make text unreadable, because nothing states which role pairs must contrast. | Vocabulary `contrast: [{ foreground, background, minimum, maximum?, lessThan?, description? }]`; `validateTheme` fails with `insufficient-contrast` naming roles and measured ratios. | §6.5, §10 | Checks WCAG 2.x relative luminance with alpha composited over the declared base, on install only. APCA is not checked. |
| LF-11 | A translucent border, text or shadow needs its own theme role per alpha step, so themes grow and drift. | A colour-typed recipe value may be `{ role, alpha }`, where `alpha` is a declared `opacity` name or 0 to 1; it also recovers under reduced transparency and forced colours. | §6.2, §6.4 | Colour authority is unchanged: the hue still comes only from the theme. |
| LF-12 | Each data source can be unauthorised, unavailable, stale or malformed, and every host invents its own wrapper, so widgets and agents cannot rely on one shape. | A documented envelope (`ok` with `value` and optional `checkedAt`, or `unauthorized`/`unavailable`/`stale`/`failed` with `reason`), the `sourceOutcome(result)` helper that builds its schema, and outcome scenarios in preview and authoring. | §5, §7.3 | A convention plus a helper, not a format rule: a host that returns a bare `result` still validates. |
| LF-13 | The in-sandbox half of a runner is private and Bun-specific, so an app with a V8 isolate, quickjs or a separate process must re-implement linking and validator wiring. | `/runner-kit` exports `renderModule()` and `linkPackage()` with a documented linker contract; `/runner-kit.bundle.js` is a self-contained import-free ES module; both reference runners are rebuilt on it. | §7.5, §13 | Not an isolation boundary: it runs inside the sandbox the host provides, and the host validates every result again. |
| LF-14 | The host ships the whole capabilities document to the browser, including operations the widget never uses. | `capabilitiesFor(capabilities, manifest)`, pure and deterministic, and `compileValidator` gives identical results on its output. | §10 | Pruning only: the host still ships validator inputs, and the manifest still declares every intent. |
| LF-15 | The seven authoring operations exist only behind a stdio MCP server, so an app with its own tool protocol cannot reuse them. | `/authoring` exports `createAuthoring()` with the seven typed operations; `liveframe mcp` is an adapter over it. | §13 | Requires the host's `runner`; loads neither the MCP SDK nor Playwright. |
| LF-16 | An agent answers with one-off JSON, but a validated tree needs derived key-path ids and a manifest, so the host synthesises both by hand. | Element JSON (`{ kind, key?, variant?, props, style?, events?, children? }`), `renderElements()`, `ephemeralManifest()`, and a JSON Schema per catalog from `generateElementsSchema()`. | §7.2, §9 | Trees are ephemeral: nothing is packaged or stored, and the surface still validates against its own manifest. |
| LF-17 | A streaming agent surface re-sends and re-validates the whole tree on every update, and nobody has measured whether patches are worth it. | A recorded benchmark: 100 revisions of a 679-node, 50-row surface at 10/s through `renderElements` and `<Surface>`, with transfer bytes, arrival validation and React commit cost. | §9 | No API change: tree patches stay unimplemented, per the measurement's decision. |

## Clay requests

| ID | Problem, in general | Shipped in 0.2.0 | Spec | Limitation |
| --- | --- | --- | --- | --- |
| CL-01 | A preview component that owns the page URL and infers which scenario a result belongs to breaks hosts with their own router or two previews on one page. | `<Preview>` requires `resultScenario`, accepts a controlled `selection`/`onSelect` that neither reads nor writes the location, and takes `urlKey` for uncontrolled pages; capture addresses `<urlKey>.scenario`. | §7.5 | Breaking: `resultScenario` is required, and URL inference is gone. |
| CL-02 | The surface's wrapper and portal container cannot be fitted into a host layout, so the host writes CSS that reaches into library markup. | `wrapperProps` and `portalProps` accept `{ className?, style? }`, merged after the scope attributes. | §11 | Host classes append to the library's and cannot override `data-lf-*`; the portal container still takes a layout box unless the host sets `display: contents`. |
| CL-03 | A published export condition names files the archive does not ship, so a resolver that honours it fails instead of falling back. | The published manifest carries no development-only condition, and the archive gate rejects any export target missing from the packed file list. | §13 | The condition still exists for in-repo resolution through `liveframe:source`; only the published manifest drops it. |
| CL-04 | "This slot paints nothing" can only be said by omitting the property or declaring a zero-alpha role, which then enters every theme and the contrast check. | The reserved keyword `"none"` on `backgroundColor`, `borderColor` and `outlineColor`, which also clears a background a sibling recipe set. | §6.2, §6.4 | A vocabulary may not declare a role named `none`; forced colours treat it as no background, so the inward edge rule applies. |
| CL-05 | Capture drives one engine, so an app whose webview is WebKit or WebView2 gets screenshots that are not what its users see. | `capture(url, { backend })` with a `CaptureBackend` interface, `playwrightBackend()` as the shipped default, and a documented snapshot format that may be `null`. | §7.5 | Only the Playwright backend ships; a screenshot is only as faithful as the backend's engine. |
| CL-06 | Most normative rules are not expressible in JSON Schema, so a host enforcing them in another language can only port the code and hope. | `conformance/corpus/` with 45 cases across all ten formats, and `conformance/hash/` with 45 canonical-hash vectors, both run by the library's own suite. | §10, §13 | Errors match on `(kind, pointer)` only, not messages; a case's expectation changes only with a format version. |
| CL-07 | Height cannot be bounded, so a list cannot be capped so a sibling stays reachable, and an empty state cannot reserve space. | `minHeight` and `maxHeight` style props, with the same domains as `minWidth`/`maxWidth` and responsive values. | §6.3 | A percentage height needs a definite containing-block height, as CSS defines. |
| CL-08 | A numeric control must encode its value as a string, and the host parses it back with no bounds check. | `carries: "number"` and `"integer"`; `emit` rejects `NaN`, infinities and a non-integer, and `bind`/`setState` compare the event type with the target schema. | §5, §8 | An integer binds to an `integer` or `number` argument; the host checks `minimum`/`maximum` on the filled value. |
| CL-09 | A host that must drop translucency — no compositor blur, low-power mode, an in-app setting, an engine without the media query — has no way to say so except host CSS on library classes. | `<Surface transparency="reduced">` sets `data-lf-transparency="reduced"`, which applies the same overrides as `prefers-reduced-transparency` and suppresses transitions on switch. | §6.4, §11 | Applies per surface, not app-wide; `auto` follows the media query. |

## Backlog items the requests raised

| Backlog item | Shipped in 0.2.0 | Limitation |
| --- | --- | --- |
| Verify conformance registrations in other runners and browsers | The browser suites run under Chromium, Firefox and WebKit via `LIVEFRAME_BROWSER`, and the platform-floor test covers `@starting-style`, container queries, `:user-invalid`, `:popover-open`, `backdrop-filter`, `font-size-adjust`, `color-mix()` and `text-wrap: balance` in each. | WebKit runs in CI on Linux; a real WebKitGTK window is still the adopter's check. |
| Placeholder and scrollbar recipe properties | `placeholderColor` and `scrollbarThumbColor`/`scrollbarTrackColor` are recipe properties; `none` is accepted; forced colours hand both to the OS. | No proof design system declares a placeholder colour, so the UA default is what ships in the proof. |
| Generated implementation types for JSON-loaded catalogs | `generateDefinitions()` emits implementation types from a catalog document, and `liveframe gen --implementations` uses it. | The catalog must still be validated first; the types follow `Infer`, not runtime data. |
| Cap or report the in-process runner's module memory | `inProcessRunner({ maxModules })` reports through `stats()` and refuses a new package past the limit with `limit-exceeded`. | The count is process-wide and modules are never unloaded. |
| Decide the Clay-derived git-status labels fixture | Closed as the owner's own code adapted from their own Clay project; no third-party licence applies. | Provenance note only; no behaviour change. |

## Not delivered, and why

- **Native Windows forced-colours and assistive-technology audit (G29).** The checklist exists at `plans/evidence/020-g29-audit.md`, and the owner waived the run for this release. The [known limitations](../CHANGELOG.md) repeat it.
- **Tree patches (`§9`).** The LF-17 measurement decided against them; see the row above.
- **An authorisation model, an approval flow, a storage backend or a layout shell.** None ship, in 0.2.0 or before: they stay the app's.
